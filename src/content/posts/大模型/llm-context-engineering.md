做多轮对话时，一个常见错觉是：模型支持的上下文越长，记忆问题就越容易解决。实际上，窗口变长只提高了容量上限，并没有自动解决噪声、成本、信息隔离和重点丢失。

上下文工程的目标不是「塞入最多的文本」，而是：**在有限 token、延迟和权限边界内，给模型提供回答当前问题所需的最小充分信息。**

## 先把上下文拆成四层

一个可维护的 Agent 请求不应只有 `messages` 数组，而应明确区分信息来源：

| 层级 | 内容 | 生命周期 | 主要风险 |
| --- | --- | --- | --- |
| 行为层 | 角色、规则、输出格式、工具约束 | Agent 级 | 指令冲突、提示注入 |
| 会话层 | 最近几轮原始消息 | 分钟到小时 | 超出窗口、跨会话串线 |
| 记忆层 | 用户偏好、阶段性摘要 | 天到月 | 过期、错误记忆、隐私 |
| 检索层 | 与问题相关的文档片段 | 单次请求 | 召回噪声、越权检索 |

这四层应有独立的数据来源和过滤规则。尤其不要让检索到的文档拥有和系统提示相同的指令优先级；外部内容是证据，不是命令。

## 用 token 预算代替消息条数

「保留最近 20 条消息」很容易实现，却不是稳定策略：20 条短消息可能只占几百 token，一段粘贴的日志却可能直接塞满窗口。

更可靠的分配方式是：

```text
上下文上限 C
├─ 系统与安全规则 S
├─ 当前用户输入 Q
├─ 计划输出 R
├─ 检索证据 K
├─ 历史与记忆 H
└─ 安全余量 M

H = C - S - Q - R - K - M
```

推荐按以下顺序装配：

1. 固定系统规则与当前问题；
2. 为回答预留最大输出和 10% 左右的安全余量；
3. 放入经过排序和去重的检索片段；
4. 从最近一轮开始，按完整的 user/assistant 对回填历史；
5. 剩余空间再加入摘要或较低优先级记忆。

估算 token 时最好使用目标模型对应的 tokenizer。若供应商不提供，可采用偏保守的字符估计，并在真实响应中采集 usage 数据持续校准。

## 短期历史：先保证完整，再追求更多

滑动窗口仍然是短期记忆的最佳起点，但要避免三种错误：

- **截断半轮对话**：留下 assistant 回答却丢掉对应问题，语义会失真；
- **忽略消息类型**：工具调用与工具结果必须成对保留；
- **跨作用域取历史**：私聊、群聊和公共频道必须使用不同的查询条件。

在 Lchat 这类系统中，历史查询应以 `conversation_id` 或严格等价的作用域为边界，而不能只按时间取「这个用户最近的消息」。群聊还要再次确认调用者当前仍是成员，防止退出群后通过 Agent 间接读取历史。

## 摘要记忆：压缩的是历史，不是事实真伪

当旧历史必须离开滑动窗口时，可以生成阶段摘要：当前目标、已经确认的事实、未解决问题和用户明确偏好。建议使用结构化格式，方便后续更新：

```yaml
goal: 为 Go 聊天服务接入模型
decisions:
  - Agent 作为独立用户
  - 使用 OpenAI-compatible API
constraints:
  - 不允许默认访问私网地址
open_questions:
  - 是否需要长期知识库
```

摘要不是绝对事实。它可能遗漏条件，也可能把模型推测写成结论。因此需要保存摘要覆盖的消息范围，让用户能够回溯原文；更新时尽量基于旧摘要和新增消息做合并，而不是每轮从头总结全部历史。

适合写入长期记忆的信息应满足至少一个条件：用户明确要求记住、在多次交互中稳定出现、对后续任务持续有用。验证码、密钥、一次性情绪和未经确认的推断都不应进入长期记忆。

## RAG：只把真正相关的证据放进来

RAG 的基本链路是「切分 → 向量化 → 召回 → 重排 → 拼装」。其中最容易被低估的是切分与重排：

- 代码文档优先按标题、函数或类边界切分，而不是固定字符数；
- 每个片段携带来源、更新时间、权限标签和稳定 URL；
- 向量召回负责扩大候选集，关键词召回补充精确名称；
- 重排器结合当前问题选择少量高价值片段；
- 相邻片段可合并，但要去重，避免同一句话重复占据窗口。

一个小知识库可以先采用混合评分：

```text
score = 0.55 × vector_similarity
      + 0.30 × keyword_score
      + 0.15 × freshness_score
```

权重没有通用最优值，必须通过自己的问题集校准。对技术文档而言，精确的标识符匹配往往比纯语义相似度更重要。

## 权限过滤必须发生在召回之前

多用户 Agent 的严重漏洞之一，是先从全库召回，再在返回答案时尝试过滤。此时越权内容已经进入模型上下文，日志、缓存或模型输出都可能泄露它。

正确顺序是：

```mermaid
flowchart LR
  Q[用户问题] --> A[确认用户与会话身份]
  A --> F[按租户/群组/文档 ACL 过滤候选域]
  F --> R[向量与关键词召回]
  R --> X[重排与上下文拼装]
  X --> M[模型生成]
```

缓存键同样要包含租户、用户权限版本与知识库版本。只用问题文本做缓存键，会把一个用户有权看到的答案交给另一个用户。

## 如何评测上下文工程

只看回答「像不像」很难定位问题。可以准备一组带标准证据的小型评测集，把链路拆开观察：

| 指标 | 回答的问题 |
| --- | --- |
| Recall@K | 正确证据是否进入候选集 |
| MRR / nDCG | 正确证据是否排在前面 |
| Context precision | 放入窗口的片段有多少真正有用 |
| Faithfulness | 回答是否能由给定证据支持 |
| Citation accuracy | 引用是否真的指向对应结论 |
| Token / latency | 每次回答的成本与耗时是否可接受 |
| Isolation tests | 是否存在跨用户、跨群组信息泄露 |

评测样本应包含正常问题、信息不足问题、互相冲突的文档、过期文档、提示注入片段和越权请求。一个能在 Demo 中答对问题的 RAG，不一定能在真实权限与脏数据下可靠工作。

## 一条够用的落地路线

对于个人或小型项目，可以按复杂度逐层增加能力：

1. token 预算 + 最近完整对话轮；
2. 结构化阶段摘要，并保留原消息范围；
3. 带来源和 ACL 的文档检索；
4. 混合召回、重排和引用；
5. 以评测数据决定是否需要更复杂的记忆代理。

上下文工程不是模型之外的装饰，而是 LLM 应用的数据层。真正可靠的「记忆」，必须同时做到相关、可追溯、不过期，并且绝不越权。
